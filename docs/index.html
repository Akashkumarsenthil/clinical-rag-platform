How this demo maps to production

What these numbers do—and do not—show

The metrics are calculated on page load from the committed synthetic corpus. They are regression signals for this demonstration, not evidence of clinical performance.

Recall@3
Share of labeled relevant chunks appearing in the first three results.
MRR
How early the first relevant chunk appears in each ranked list.

Limitation: A ten-chunk synthetic set is intentionally understandable, but too small and clean for model selection or safety claims.

Reliability and tradeoffs

Designed for failure, not just the happy path.

↻

Idempotent ingestion

SHA-256 file hashing and UUID-5 identifiers prevent duplicate document records. Existing vectors are deleted by doc_id before an upsert.

△

Graceful retrieval

Dense and sparse retrievers are isolated. One path can still contribute candidates when the other fails; the request fails only when both return nothing.

◎

Observable stages

Redis tracks pipeline progress, Postgres records status and errors, Prometheus exposes service metrics, and OpenTelemetry tracing is best-effort.

⌁

Scoped evidence

Document chat applies a Qdrant payload filter and builds a doc-scoped BM25 index, then performs an additional metadata safety filter before fusion.

Current limitations

  • No authentication or tenant isolation is implemented.
  • The API currently allows broad CORS and needs production hardening.
  • BM25 is in-memory and is rebuilt from Qdrant state.
  • Confidence is a heuristic—not calibrated clinical certainty.
  • No repository-backed large-scale retrieval evaluation is committed.

What I would improve next

  • Add role-based access, encryption, retention controls, and audit logs.
  • Version indexes and evaluate retrieval on a larger reviewed corpus.
  • Add reranker and answer-groundedness regression datasets.
  • Bound uploads, sanitize filenames, and add malware scanning.
  • Calibrate abstention thresholds before any high-stakes use.
